Most of the time, you don't need to know what a CPU is doing. You write a function, it runs. But there's a point where the abstraction stops being enough — where you need to understand what's actually happening at the hardware level to reason about performance, or bugs, or why something behaves the way it does.

This is my attempt to write down what I learned.

The fetch-decode-execute cycle

At its core, a CPU does three things in a loop:

  1. Fetch — retrieve the next instruction from memory
  2. Decode — figure out what that instruction is asking
  3. Execute — do it

That's it. Everything else — pipelines, caches, branch prediction — is an optimisation on top of this basic loop.

Where instructions live

Instructions are stored in memory as binary. The CPU keeps track of which instruction to fetch next using a register called the program counter (PC). After each fetch, the PC increments. When you call a function, the PC jumps to that function's location in memory. When the function returns, it jumps back.

This is why a stack overflow is called that — function calls push a return address onto the stack, and if you recurse too deep, you run out of stack space.

Registers

The CPU doesn't work directly with memory most of the time. It loads values into registers — small, extremely fast storage slots inside the CPU itself — does the computation, then writes the result back to memory if needed.

This is why you see assembly instructions like MOV (move a value into a register) and ADD (add two registers together). The compiler's job, in part, is to figure out which variables get to live in registers and which have to go to memory.

What this changed for me

Understanding this made a lot of things click. Why local variables are fast. Why function calls have overhead. Why certain patterns in high-performance code look the way they do.

The abstraction is useful — but knowing what's underneath it makes you a better programmer, even when you never need to think about it directly.
